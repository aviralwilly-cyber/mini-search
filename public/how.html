how mini-search works

← back to the search

A search engine written from scratch in TypeScript — no Elasticsearch, no Lucene, no search libraries of any kind. The tokenizer, stemmer, inverted index, BM25 ranking and trie autocomplete are all hand-written. It indexes 100,000 Hacker News stories and comments and answers queries in well under a millisecond.

01The problem

Why not just read every document?

Imagine 100,000 documents and someone asks for every one mentioning dragon. The obvious approach is to open document 1, read it, open document 2, read it, and so on. That works, and it is unbearably slow — the cost grows with the size of the collection, so every document you add makes every future query slower.

The fix is the same one textbooks have used for centuries: build an index once, then look things up instead of reading everything.

02Analysis

Turning messy text into clean terms

Raw text can't go straight into the index. Running, running, and RUNNING should all be the same thing, and HTML markup shouldn't be searchable at all. So every document passes through a pipeline before it's indexed.

The invariant that matters most. Queries run through the identical pipeline. If indexing and querying ever disagree — even by one rule — a query for "compilers" looks up a term that was never stored, and search silently returns nothing. Not an error, just empty results. Both paths call one shared analyze() function for exactly this reason.

03Ranking

BM25: deciding what goes first

Finding matching documents is the easy half. Ten thousand documents contain "rust" — which one does the searcher actually want? BM25 is a ranking function from the 1990s that's still the default in Elasticsearch and Lucene today. It balances three signals.

Rarity (idf). A word appearing in every document tells you nothing. A word appearing in twelve documents is a strong signal. Rarity is measured as ln(1 + (N − df + 0.5) / (df + 0.5)), where df is how many documents contain the term.

Repetition (tf), with diminishing returns. A document mentioning "rust" nine times is probably more about Rust than one mentioning it once. But fifty mentions versus fifty-five tells you almost nothing extra. The parameter k1 controls where that curve flattens.

Length (norm). A five-thousand-word comment will contain your query word eventually, purely by chance. A six-word headline containing it is far more likely to be about it. The parameter b controls how hard long documents are penalised — at b = 0 length is ignored entirely, at b = 1 it applies in full.

Both parameters are exposed as live sliders on the search page, and results re-rank as you drag. Pulling b to zero is the most striking one — long comments immediately take over the top of the results.

04Memory layout

Why the index is flat arrays, not objects

The natural way to store this in JavaScript is Map<string, {docId, termFreq}[]>. That works, and it cost 181 MB for 1.9 million postings — roughly 96 bytes each to hold two integers that need eight.

The overhead is V8's. Every posting is a separately allocated heap object with a header and a hidden-class pointer, and every posting list is an array of pointers to those scattered objects. Iterating a list means chasing pointers all over the heap, so it's slow for cache reasons on top of being large.

Scoring accumulated results in a Map<docId, score>, which meant a hash operation per posting — 11,600 of them for a common term. Replacing it with a Float64Array indexed by docId, plus a list of touched ids so the reset costs the same as the scoring did, removed that entirely.

An equivalence test asserts both implementations return byte-identical rankings, so the optimisation is provably behaviour-preserving.

05Autocomplete

A trie, and the trap inside it

Suggestions come from a trie — a tree where each level is one letter. Following d → r → a lands on a node whose subtree contains every word starting with "dra". Each word is weighted by how many documents contain it, so common terms surface first.

The naive version descended to the prefix node and then enumerated its whole subtree. That's fine for a long prefix and catastrophic for a short one: typing a single letter meant walking a subtree holding a large share of the 68,000-word vocabulary. Measured cost was 16.4 ms for "a" against 0.6 ms for "goo" — a 26× spread from one keystroke.

The fix is a bottom-up pass after construction. Each node merges its children's top-10 lists plus its own word, and keeps the best 10. The key insight is that a word which didn't make a child's top-10 can't make the parent's either, so each merge is bounded by childCount × 10 rather than by subtree size.

06Honesty

Known limitations

Everything above describes what works. These are the parts that don't, and they're listed because knowing where a system is weak is more useful than pretending it isn't.

  • Contractions break. The tokenizer splits on non-alphanumerics, so don't becomes don plus a discarded t. C++ becomes c.
  • The stemmer is crude. It's suffix-stripping, not the real Porter algorithm, so running stems to runn and doesn't collapse with runs. Autocomplete occasionally shows both google and googl as a result.
  • No phrase queries. Searching "machine learning" finds documents containing either word, not the phrase. Real phrase support needs positional postings, which changes the index structure.
  • No typo tolerance. A misspelled query finds nothing. A BK-tree or Levenshtein automaton would fix this.
  • Near-duplicates survive. Exact title matches are deduplicated at ingest, but resubmissions with slightly different titles still appear twice. SimHash or MinHash would catch them.
  • Purely lexical. There's no semantic understanding — a search for "car" won't find "automobile".
  • The index is rebuilt at startup rather than loaded from a serialized form, costing about 3.6 seconds on boot.

07Stack

What's actually in it

TypeScript in strict mode with noUncheckedIndexedAccess, Node 22, and Fastify for the HTTP layer. Vitest for the test suite, which includes a brute-force reference implementation the index is checked against. The frontend is a single static HTML file with no build step, no framework, and no dependencies — for a UI this small, that's a smaller thing to maintain and one fewer process to deploy.

The corpus comes from the public Hacker News Algolia API, deduplicated and HTML-stripped at ingest, stored as newline-delimited JSON so it can be streamed rather than parsed whole.
